# U1.1 — Canonical admission + unified read-model architecture decision

## Primary lane

Platform/governance. Secondary: Human curation.

## Why this exists

An accepted candidate currently stops at `eligible`. Before adding T-P2 or changing the browser,
the repo must rule how legacy CSVs, the corpus store, generated projections, IDs, sources, and
browser relate. This must not be guessed in code.

R0 also settled the product boundary this design must serve: **Passage** is the durable domain
object; the current religious/philosophical corpus is seed inventory; Garden is the specialized
passage product; Initiate is a broader memory lifecycle and is neither required for nor authoritative
over Garden.

## Inputs / dependencies

Gate U0 accepted; Product Doctrine; DATA_CONTRACT; STATE_MODEL; browser parser/architecture; Pages contract; store schema/export; candidate envelope; current 324-row CSVs; W0/W1 projection doctrine; unresolved ontology/source questions.

## In scope

Produce a decision/spec comparing at least:

A. mutate `quotes.csv`/`sources.csv` on admission;
B. migrate all authority into the store now;
C. keep legacy inputs + store authority and generate a deterministic unified Garden read model.

Evaluate each against:
- one writable authority per fact;
- provenance;
- reversibility;
- existing 324-row stability;
- stable IDs for new items;
- `source_id`/source behavior;
- browser compatibility;
- clean-clone rebuild;
- deterministic diffability;
- canonical ≠ verified;
- future research/exploration compatibility;
- Passage semantics beyond the current legacy “quote” inventory;
- no hard dependency on Initiate and no duplicate mutable authority across repos.

Define:
- authoritative vs derived artifacts;
- minimum Garden-facing admission metadata;
- ID strategy;
- research_state → visible verification projection;
- source/source_id rules;
- canonical withdrawal/retirement rule;
- exact derived read-model schema/location/version;
- whether generated output is committed;
- how it is validated.

Preferred hypothesis is option C, but the unit must earn that ruling.

## Out of scope

No T-P2 implementation, migration, projection generator, browser change, ontology cleanup,
Initiate adapter, shared cross-repo store, or generalized memory-object model.

## Human gates

The architecture decision is operator/frontier authority. Builder may recommend; operator accepts/rejects before U1.2.

## Acceptance criteria

One decision document answers every bullet above and contains no dual writable authority. Existing browser assumptions are measured, not assumed.

## Evidence required

Architecture comparison table, browser/schema assumption inventory, one worked example of a new accepted-but-unverified candidate through the proposed read model, reversibility walkthrough.

## Stop condition

PR/evidence ready → architecture synthesis. Do not implement U1.2 until operator records the decision.

## Builder prompt

Execute U1.1 as an architecture/ruling unit only.

Inspect the actual current parser, data contract, store export, state model and Pages deployment. Compare the three authority/projection architectures. Use the preferred "legacy inputs + store + deterministic derived unified read model" only as a hypothesis.

Do not code T-P2 or switch browser inputs.

Your deliverable must make it impossible for U1.2/U1.3 to accidentally create a second writable authority. Define the minimum admission metadata and all projection rules, including ID, source behavior and canonical-but-unverified display.

Create `GARDEN_U1_1_HANDOFF.md`, open one PR, and stop for foreign QA + operator architecture synthesis.

## Foreign QA prompt

Attack U1.1 for hidden dual authority and missing edge cases.

Trace one new candidate, one legacy row, one unverifiable row, and one canonical withdrawal through the proposed model.

Inspect browser/parser assumptions and identify any fields/ID types the proposal forgot.

Reject a design if generated projection can be hand-edited as truth, if two systems can independently write the same fact, or if canonical admission silently implies verification.

Return architecture blockers and a recommended operator verdict. Do not implement.
